# pdf-rag

Маленький, но честный RAG: кладёте PDF — задаёте вопрос — получаете ответ
с точной цитатой и номером страницы источника.

Postgres + pgvector для хранения и поиска, локальные эмбеддинги (без API-ключа),
Claude для генерации ответа. Никаких LangChain и прочих фреймворков — весь
конвейер видно целиком: ~950 строк вместе с комментариями, из них на сам RAG
(чтение, нарезка, векторы, поиск, генерация) приходится около 600.

```
PDF → текст постранично → чанки → векторы → Postgres/pgvector
                                                    ↓
                    вопрос → вектор → ORDER BY embedding <=> query LIMIT k
                                                    ↓
                                    top-k фрагментов + вопрос → Claude
                                                    ↓
                                    ответ + цитаты со страницами
```

## Зачем это вообще нужно

У языковой модели две проблемы с вашими документами: она их не видела (они не
были в обучении), и целиком в контекст они не влезают. RAG решает обе — находит
несколько релевантных кусков и кладёт в контекст только их.

Побочный, но главный для практики эффект: ответ становится **проверяемым**.
Модель отвечает не «из головы», а по конкретным фрагментам, и на каждый факт
есть ссылка на страницу.

## Быстрый старт

Нужны Python 3.11+ и Docker.

```bash
git clone <ваш-репозиторий> && cd pdf-rag

python -m venv .venv
.venv\Scripts\activate          # Windows
# source .venv/bin/activate     # Linux / macOS
pip install -r requirements.txt

cp .env.example .env            # Windows: copy .env.example .env
# впишите ANTHROPIC_API_KEY (или сделайте `ant auth login`)

docker compose up -d            # Postgres 17 + pgvector на порту 5433
python -m rag init              # таблицы и HNSW-индекс

python scripts/make_sample_pdf.py   # тестовый договор, если своих PDF ещё нет
python -m rag ingest ./docs

python -m rag ask "What is the warranty period?"
```

Свои PDF просто кладите в `docs/` и повторяйте `ingest` — русские документы
работают, модель эмбеддингов мультиязычная.

## Команды

| Команда | Что делает |
|---|---|
| `python -m rag init` | Создать таблицы и индекс |
| `python -m rag ingest ./docs [--force]` | Проиндексировать PDF (файл или папку) |
| `python -m rag search "запрос"` | **Только поиск, без модели** — видно, что находит RAG |
| `python -m rag ask "вопрос" [--show-chunks]` | Поиск + ответ Claude со ссылками |
| `python -m rag stats` | Что лежит в базе |
| `python -m rag reset` | Снести и пересоздать таблицы |
| `streamlit run app.py` | Веб-интерфейс (см. ниже) |

`search` — самая полезная команда для понимания RAG. Плохой ответ почти всегда
означает, что поиск принёс не те фрагменты, а не что модель «глупая». Сначала
смотрите `search`, потом чините промпт.

**Ключ Anthropic нужен только для `ask`.** Индексация, `search`, `stats` и
просмотр базы в веб-интерфейсе работают полностью офлайн — эмбеддинги считаются
локально. Можно изучать поиск, не потратив ни цента.

## Веб-интерфейс

```bash
streamlit run app.py     # http://localhost:8501
```

Четыре вкладки:

- **📚 Документы** — перетащить PDF, проиндексировать, посмотреть список,
  удалить лишнее. Загруженные файлы кладутся в `docs/`.
- **🔍 Поиск** — что находит векторный поиск, со шкалой сходства и полным
  текстом каждого фрагмента. **Без модели и без ключа.** Главный инструмент
  отладки: если ответ мимо, причина видна здесь.
- **💬 Вопрос** — ответ Claude с раскрывающимися цитатами. Единственная
  вкладка, которой нужен ключ; без него показывает, что делать.
- **🩺 Диагностика** — версии Postgres и pgvector, наличие HNSW-индекса,
  сверка размерности модели с типом колонки, статистика нарезки. Если
  чанков меньше ~1.2 на страницу, вкладка предупредит: куски слишком
  крупные, поиск будет промахиваться.

## Повседневная работа

База живёт в докеровском томе и переживает перезагрузки — переиндексировать
каждый раз не нужно.

```bash
docker compose start          # поднять базу (после перезагрузки компьютера)
docker compose stop           # погасить, данные остаются
docker compose ps             # проверить: должно быть healthy

docker compose down           # снести контейнер, данные остаются в томе
docker compose down -v        # снести ВМЕСТЕ с данными — придётся индексировать заново
```

Добавить свои документы:

```bash
cp ~/договоры/*.pdf docs/     # или просто перетащите файлы в папку docs/
python -m rag ingest ./docs   # уже проиндексированные пропустятся сами
python -m rag stats           # проверить, что попало в базу
```

Дедупликация идёт по содержимому файла (sha256), а не по имени: повторный
`ingest` той же папки ничего не сломает и не задублирует. Изменили PDF —
он переиндексируется. Хотите пересобрать принудительно — `--force`.

Поменяли `CHUNK_TARGET_CHARS` или `TOP_K` в `.env` — этого достаточно для
`search`, но после смены размера чанка нужен `ingest --force`: нарезка
уже лежит в базе.

## Как это устроено

### 1. PDF → текст ([`rag/pdf.py`](rag/pdf.py))

`pypdf` достаёт текст постранично. **Номер страницы протаскивается через весь
конвейер** — без него ссылка «этот факт из файла на 200 страниц» бесполезна.

Извлечённый текст сразу чистится: склеиваются слова, разорванные переносом
(`инфор-\nмация`), одиночные переносы внутри абзаца превращаются в пробелы.
Иначе мусор вёрстки попадёт в эмбеддинги и испортит поиск.

Сканы без текстового слоя не поддерживаются — для них нужен OCR.

### 2. Нарезка ([`rag/chunking.py`](rag/chunking.py))

Страница целиком — плохая единица поиска: один вектор на пять разных мыслей,
«среднее по больнице». Режем на куски ~1000 символов.

Две детали, которые отличают рабочую нарезку от наивной:

- **Режем по границам абзацев и предложений**, а не по символам. Абзац →
  если длинный, предложения → если и они длинные, только тогда жёстко.
- **Перекрытие 150 символов.** Хвост предыдущего чанка переносится в
  следующий. Без этого фраза, разрезанная ровно по границе, не найдётся
  нигде: в первом чанке половина, во втором вторая, ни один не похож на запрос.

Номера страниц восстанавливаются через смещения: страницы склеиваются в один
текст, запоминается стартовое смещение каждой, а страница чанка ищется
бинарным поиском. Поэтому чанк честно знает, что он «стр. 2–3».

#### Почему размер чанка — не косметика

Это замер на `docs/sample_agreement.pdf`, запрос
*«How much notice to terminate the agreement?»*. Нужный пункт — на стр. 2.

| `CHUNK_TARGET_CHARS` | Чанков | Сходство нужного фрагмента | Позиция в выдаче |
|---|---|---|---|
| 1000 | 3 | 0.431 | 3-я ❌ |
| 600 | 4 | 0.745 | 1-я ✅ |
| 350 | 8 | **0.807** | 1-я ✅ |

При 1000 символов страница договора влезала в один чанк целиком — и «оплата»,
и «расторжение» попадали в **один вектор**. Усреднённый отпечаток не совпал ни
с одним запросом, а на первое место вылезла стр. 1, просто потому что там много
раз встречается слово «agreement».

Мораль: если RAG отвечает мимо, первый подозреваемый — не промпт и не модель,
а размер чанка. Поэтому дефолт здесь 600, а не «круглая тысяча».

### 3. Эмбеддинги ([`rag/embeddings.py`](rag/embeddings.py))

Вектор — это смысл текста в виде ~400 чисел. Похожие по смыслу тексты дают
близкие векторы, даже если слов общих нет: «Сколько длится гарантия?» найдёт
«Гарантийный срок составляет 24 месяца».

**У Anthropic нет embeddings API** — это отдельная модель, её берут отдельно.
Здесь `fastembed` (onnxruntime, без torch) считает всё локально: бесплатно,
офлайн, детерминированно. По умолчанию
`paraphrase-multilingual-MiniLM-L12-v2` — 384 измерения, ~220 МБ, знает русский.

Тонкость про **асимметричный поиск**: вопрос и абзац выглядят по-разному, и
модели семейства E5 просят помечать их префиксами `query:` / `passage:`.
Для моделей, которые этого не ждут, префиксы наоборот вредят — поэтому код
смотрит на имя модели.

Хотите точнее на русском — в `.env` есть закомментированный
`intfloat/multilingual-e5-large` (1024 измерения, ~2.2 ГБ). После смены модели
обязателен `python -m rag reset`: размерность зашита в тип колонки.

> **Спрашивайте на языке документа.** Замеренная на дефолтной модели картина:
> на запрос «Сколько длится гарантия?» русский абзац про гарантию даёт сходство
> `0.526`, английский абзац **про то же самое** — всего `0.407`, то есть ниже,
> чем нерелевантный русский абзац про расторжение (`0.442`). Межъязыковой поиск
> у `paraphrase-multilingual-MiniLM` слабый: русский вопрос к английскому PDF
> найдёт не то. Для смешанной по языкам базы берите `multilingual-e5-large`.

### 4. Хранение и поиск ([`rag/db.py`](rag/db.py))

```sql
CREATE EXTENSION vector;

CREATE TABLE chunks (
    id          BIGSERIAL PRIMARY KEY,
    document_id BIGINT NOT NULL REFERENCES documents(id) ON DELETE CASCADE,
    page_start  INT    NOT NULL,
    page_end    INT    NOT NULL,
    content     TEXT   NOT NULL,
    embedding   VECTOR(384) NOT NULL
);

CREATE INDEX ON chunks USING hnsw (embedding vector_cosine_ops);
```

Весь поиск — это один запрос:

```sql
SELECT content, embedding <=> %s AS distance
FROM chunks ORDER BY distance LIMIT 5;
```

`<=>` — косинусное расстояние из pgvector: `0` — про одно и то же, `1` — про
разное. Поэтому всегда `ORDER BY ... ASC`, без `DESC`.

`HNSW` — приблизительный поиск ближайших соседей. На сотне чанков разницы не
видно, на миллионе именно он делает поиск возможным: без индекса Postgres
честно сравнил бы запрос с каждой строкой.

Почему Postgres, а не отдельная векторная БД: вектор лежит рядом с обычными
колонками, и фильтры («только договоры за 2026 год») — это обычный `WHERE`
в том же запросе, без синхронизации двух хранилищ.

Дедупликация идёт по `sha256` файла, а не по имени: переименованный дубликат
не попадёт в базу дважды.

### 5. Ответ со ссылками ([`rag/answer.py`](rag/answer.py))

Обычно на этом шаге просят модель расставлять `[1]`, `[2]` вручную. Работает,
но модель иногда ссылается на источник, которого в контексте не было.

Здесь используется **встроенное цитирование Anthropic**: каждый фрагмент уходит
как блок типа `document` с `citations: {"enabled": true}`. В ответе
процитированные куски текста приходят с полем `citations`, где лежит точная
выдержка (`cited_text`) и индекс документа. Цитату формирует API по реальному
тексту фрагмента — **выдумать её нельзя**.

Системный промпт запрещает добавлять что-либо от себя и прямо требует сказать
«в документах ответа нет», если его там нет. Включено adaptive thinking — оно
заметно помогает честно признать отсутствие ответа вместо правдоподобной выдумки.

## Что можно улучшить дальше

Осознанно не сделано, чтобы конвейер оставался читаемым:

- **Гибридный поиск.** Векторный поиск плохо ищет точные строки — артикулы,
  номера статей, фамилии. Лечится добавлением полнотекстового поиска Postgres
  (`tsvector`) и объединением двух списков через Reciprocal Rank Fusion.
- **Реранкер.** Достать топ-50 дешёвой моделью и переранжировать кросс-энкодером —
  обычно самый заметный прирост качества на один вложенный час.
- **Оценка качества.** Набор из 30 вопросов с эталонными ответами и метрика
  «в скольких случаях нужный чанк попал в топ-5». Без этого улучшения
  конвейера — угадывание.
- **OCR** для сканов и **семантическая нарезка** по смысловым границам.

## Если что-то не работает

**Первый `ingest` висит на «Fetching 5 files» и байты не идут.**
Скачивание модели через новый бэкенд Hugging Face (`hf-xet`) на Windows умеет
вставать намертво: файлы создаются нулевого размера, прогресс замирает на 60 %.
Лечится переключением на обычный HTTP:

```bash
set HF_HUB_DISABLE_XET=1          # Windows (cmd)
$env:HF_HUB_DISABLE_XET=1         # Windows (PowerShell)
export HF_HUB_DISABLE_XET=1       # Linux / macOS
```

Если уже повисло — удалите `local_cache/` и запустите заново с этой переменной.

**`could not translate host name` / `connection refused` на порту 5433.**
База не поднята: `docker compose up -d`, затем `docker compose ps` — статус
должен быть `healthy`.

**`expected 384 dimensions, not 1024`.**
Сменили модель эмбеддингов, но таблица осталась старой. Размерность зашита в тип
колонки `VECTOR(n)`, поэтому: `python -m rag reset` и переиндексировать.

**`ingest` says «не удалось извлечь текст».**
PDF — это скан без текстового слоя. Нужен OCR (например, `ocrmypdf`), `pypdf`
такое не вытащит.

**Ответ невпопад.** Сначала посмотрите `python -m rag search "ваш вопрос"`.
Если нужного фрагмента нет в выдаче — проблема в поиске (размер чанка, модель
эмбеддингов, `TOP_K`), а не в промпте.

## Структура

```
rag/
  config.py      настройки из .env
  pdf.py         PDF → страницы текста
  chunking.py    страницы → чанки с номерами страниц
  embeddings.py  текст → вектор (fastembed, локально)
  db.py          схема, вставка, векторный поиск
  ingest.py      конвейер индексации
  answer.py      фрагменты + вопрос → Claude с цитатами
  __main__.py    CLI
app.py           Streamlit-интерфейс
scripts/         генератор тестового PDF
```
